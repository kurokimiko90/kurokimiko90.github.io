CORE CAPABILITIES

できることを、
証拠と一緒に置く。

五つの能力を、実際の成果物に紐づけて並べています。
★ の二つは、他の PdM と比べたときの差だと考えている点です。

  1. 01

    合意をつくる

    曖昧な要求を、決められる形のリストに変える。

    仕様の違いや利用者の役割を整理し、判断を誰に戻すかまで決める。共通にできる部分と、残すべき例外を分けて扱う。

    ポイント・会員システム
    UI・開発・テストの 3 チームと、テスト・検収 250+ 項目を共通の確認軸に。
    予約 SaaS
    admin 4 ロールと購入者ペルソナを定義し、5 業態ごとに料金・在庫の階層を個別検証。
  2. 02

    PM の基礎を通す

    要求から PRD、受入条件まで、同じ文書系列で通す。

    調査で前提が変われば作る方向も変える。何を優先し、何を引き受けるかを、版管理された成果物として残す。

    予約 SaaS
    PRD を v2.5→v2.7 に反復。TECHNICAL / API / SPRINT_SPEC / TEST_CASES / FAILURE_MODES を版管理して一式納品。
    ProManager
    24 の PdM Agent と S1–S7 の工程・Gate を実装。「已完成」と「已検証」を別概念として扱う。
  3. 03

    技術を読み書きする

    アーキテクチャの判断を自分で書き、コードを読んで直せる。

    エンジニア出身の PdM として、仕様の実現方法まで踏み込む。実装をすべて自分で行うという意味ではなく、判断の根拠を技術側と同じ言葉で持つということ。

    JobPilot
    ルール採点と LLM 分析を工程で分離。採点コードとマスキング処理を抜粋公開。
    Miko Agent
    72 の SKILL.md（skills/ 配下 71 + ルート 1）、7 つの強制工程、4 段階の Risk tier。2026-09-08 時点のリポジトリ実査。
  4. 04

    AI を仕組みで御する★

    聞き方がうまい、ではない。失敗したときに何が起きるかを設計する。

    一度動くデモと、毎日動く仕組みは別物として扱う。品質のしきい値、失敗時の切替、コストの上限を、運用側の条件としてコードに置く。

    Project Miko
    LLM を 3 段で切替。成功率 85% 未満は次工程へ進めない品質ゲート。呼出回数 12→1 回の削減を品質維持を確認した上で実施。
    Samurai
    トークンを記帳し、session / 5h / 日次の 3 段で自動停止。役割別 Bot 4 本と定期実行 11 本を常駐運用。
  5. 05

    多言語の品質を担保する★

    中国語・日本語・簡体字の三方向。日本語の検収語彙で受入条件まで書く。

    翻訳の可否ではなく、抜けたときに何が壊れるかで見る。文言の不足を不具合として受入基準に載せ、リリース判定の対象にする。

    予約 SaaS
    購入者向けサイトの i18n メッセージキーを 1 → 319 に拡張。多言語メールの対応漏れを P0 ブロッカーとして特定し、受入基準へ明記。
    会員システム
    プロトタイプから日中の言語パック対応まで主導し、3 チームの協業を推進。

数値は担当業務の記録と、2026-09-08 時点のリポジトリ実査に基づきます。売上や導入数など事業成果の指標とは分けて記載しています。
