AT A GLANCE / 07 POINTS

  1. 01案件

    レジャー体験の自社直販を支えるマルチテナント予約 SaaS。購入者向けサイト・管理画面・スケジューラーの 3 システム構成を 0.2→1 で立ち上げ。

  2. 02なぜやるか

    購入者の予約画面だけを見ていると、運営者の料金・在庫・消し込み・精算が設計から抜け落ちる。参入する場所を決め直す必要があった。

  3. 03どう考えたか

    競合 10 社の機能比較と主要チケット 5 サービスの分析、管理画面の調査から、当初のポジショニングを覆した。

  4. 04出したもの

    PRD を v2.5→v2.7 に反復。PRD / TECHNICAL / API / SPRINT_SPEC / TEST_CASES / FAILURE_MODES を版管理して一式納品。非技術者向け運用マニュアルを 3 システム分。

  5. 05協働の仕方

    開発・検証・事業関係者と協働。admin 側 4 ロール（スーパー管理者 / 運営 / テナント / 経理）と購入者ペルソナを定義し、誰の作業かを分けた。

  6. 06AI の使い方

    全画面の HTML プロトタイプを Claude Code で自作し、そのまま実装へ渡した。文章を書かせるためではなく、合意を早めるための試作に使っている。

  7. 07私の担当

    PdM として主責（市場分析・要件・UX・リスク整理・納品）。実装は開発チーム。RBAC 権限、i18n キー拡張、構造化ログの一部は自分で手を動かした。

01 / SUMMARY

「予約を売る」の先に、どの業務を支えるか。

予約プロダクトを作るとき、購入者の予約画面だけを見ていると、運営者が何に困るかを取りこぼします。販売、料金、在庫、消し込み、精算までを含めて、参入する場所を考える必要がありました。

競合と主要なチケットサービスを分析し、当初の位置づけを見直しました。焦点を置いたのは、レジャー体験の自社直販と、それを支える運営の仕組みです。

02 / RESPONSIBILITY

調査の結論を、実際の仕様まで持っていく。

市場分析とポジショニング、要件、プロトタイプ、リスク整理、開発・検証への引き継ぎまでを担当しました。購入者向けサイトと管理側の業務を、両方の視点から設計しています。

PRD、技術・API の資料、スプリント仕様、テストケース、失敗モードをバージョン管理し、非技術者向けの運用資料も整備しました。

03 / CONSTRAINTS

同じ「予約」でも、運営の前提が違う。

複数の業態では、料金の組み方や在庫の階層が異なります。購入者には簡潔な体験を提供しながら、運営、テナント、経理などの権限と作業を分ける必要がありました。

特に在庫の引当と決済の前後関係は、正常系の画面だけでは設計できません。途中で失敗したときに、どの状態へ戻すかまで検証対象にしました。

04 / INSIGHT

競合の機能表を、参入する理由に変える。

競合の機能比較と主要プラットフォームの分析、管理画面の調査を行いました。その結果を受けて、レジャー体験・決済と自社直販のバックエンドへ位置づけを変更しています。

ここで根拠としたのは市場・競合資料と業務の整理です。顧客インタビューによって需要を実証した事例としては扱っていません。

05 / KEY DECISION

広く作るより、支える業務を定める。

直販と運営支援に焦点を定めたことで、役割、料金、在庫、精算といった設計対象が明確になりました。見た目の予約機能だけでなく、誰が何を操作し、その結果がどこへ伝わるかを定義しました。

この方向では業態差や権限、例外系の設計を引き受けます。機能を並べるだけでは済まない複雑さを、受入条件や運用資料まで持ち込む判断です。

  • 市場：自社直販と運営支援に焦点を置く
  • 体験：購入者と管理側の役割を分ける
  • 品質：在庫と決済の失敗条件を受入へ含める

06 / DESIGN

例外の扱いも、プロダクトの一部。

管理側の役割と操作権限、業態ごとの料金・在庫の扱いを整理しました。在庫引当が失敗した場合のロールバックや、多言語メールの不足などを、受入で確認する項目として明記しています。

PRD とプロトタイプを反復し、開発に必要な仕様と、使う側が必要な運用説明を一式にしました。以下は実際の画面ではなく、設計範囲を説明する図です。

07 / REFLECTION

戦略の変更と、市場での成果は分けて考える。

この事例で示す成果は、参入ポジションの変更と、それを反映した設計・納品物です。売上、導入数、予約転換率の向上を示す定量データは掲載していません。

次の検証では、想定した運営者が実際に料金・在庫を設定できるか、例外時に復旧できるかを確認したいと考えています。市場分析で選んだ方向を、実際の業務で確かめる段階が必要です。
